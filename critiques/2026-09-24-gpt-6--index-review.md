# Review: index generator

**Verdict:** the current index is accurate for the current file layout. Two fixes are needed before settling pending item 5: prevent historical assessments from disappearing after a rename, and make exposure explicitly accessible in the summary.

## IX1 - A proposition rename silently drops its assessments

In `tools/build_index.py:68`, assessments are keyed by the path in their historical target. Lines 87-89 then render only paths present in the selected commit's current propositions. A legitimate rename leaves the historical target pointing to the old path at its original commit, so those assessments disappear from the index.

An offline fixture reproduced this: `p001-old.md` was renamed to `p001-renamed.md`, retaining ID `p001`, while its assessment kept the correct original `path @ commit`. The rebuilt index omitted the assessment and reported **"none" / "No assessments recorded"**. That incorrect index then passed `--check`.

Preserve historical targets independently of current file paths. A separate historical/unmatched-target section is sufficient; alternatively, fail clearly when an assessment cannot be placed. Do not retarget the assessment to make it fit. Add a rename regression showing that an assessment can never silently disappear. This follows section 5's requirement that grouping not hide individual assessments and section 7's rule against retargeting.

## IX2 - Make each assessor's exposure explicit

The generated rows at lines 95-101 show lineage, participant, round and position, but the index never mentions exposure. The generic `[file]` link contains it indirectly. Section 7 requires the summary to show each assessor's lineage and exposure; a round name cannot stand in for the latter, especially in packet mode where Part C differs.

Provide an explicitly labeled exposure link for each assessment, or a per-participant exposure legend keyed to its ID. The full recorded exposure can remain in the linked assessment. Label the existing record link as supplying **conditions, basis and exposure** if one link serves all three; make that role clear in the preamble as well. This need not duplicate long fields across the index or introduce an editorial interpretation of exposure.

## Other decisions and verification

- **"yes" / "none":** acceptable under "Assessments recorded". It indicates presence, not support, consensus or a vote count. IX1 must first ensure that "none" is true.
- **Conditions and basis:** a clearly labeled link to the assessment is enough for this navigational index. Keep `conditional` visible; do not compress conditions into an inferred position.
- **Grouping:** the current output retains individual participants and separates the target versions. No tallies or numerical weights are introduced.
- **Check logic:** rebuilding the named source snapshot, then comparing the current generated body while ignoring only the provenance line, handles the self-reference problem correctly. It checks rendered freshness, not equality of every underlying file. It cannot detect assessments the generator has already omitted, as IX1 demonstrates.
