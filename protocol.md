# Protocol

This file sets out how the project's files are organized, written, and changed. It does not settle any substantive moral proposition. Its own rules involve normative choices about participation, dissent, and authority, and those choices are open to challenge like anything else. When the founder adopts this protocol or any other shared document, that is a process decision, not an endorsement of any proposition. A founder's endorsement of a proposition is an attributed assessment (section 7), like anyone else's.

**Effect.** This protocol takes effect when the project goes live. Until then, the founder may direct the editor to delete or restructure files without the records this protocol would otherwise require. Founder's words, verbatim: "cleanup old file since we're not officially production ready, and u can delete files now. once we go live rules apply".

**Pre-launch history.** The public repository starts from a single launch commit. The founder keeps the git history from before launch as a private archive, and it is not published. Commit hashes in files that predate the launch commit refer to that archive and can't be checked publicly. Founder's words, verbatim: "start with clean commit, and don't push to my personal account we'll create a separate one for it".

## 3. Ownership and editing

- **Participant-owned files** are everything in `proposals/`, `propositions/`, `cases/`, `critiques/`, `questions/`, `simulations/`, `rounds/*/responses/`, and `origin/inputs/`. Only a file's author changes its content or lifecycle.
- **Shared documents** are `README.md`, `summary.md`, `CONTRIBUTING.md`, `THIRD-PARTY-NOTICES.md`, `protocol.md`, `statement.md`, and the records in `moderation/`, including `moderation/rules.md`.
  - Adopting `moderation/rules.md` authorizes the editor to create and update moderation records as those rules require, without a separate proposal for each record.
  - Only the editor changes them, and only to apply a change that was either proposed, reviewed, and adopted, or explicitly requested by the founder.
  - The commit links the proposal, the review, and the decision.
  - Each shared document lists its `contributors`. A contributor is removed from that list in only three cases:
    - to correct a mistaken attribution
    - at the contributor's own request, which is project policy
    - when a licensor requests it under CC BY 4.0 section 3(a)(3). This applies only to that licensor's material, and to the extent reasonably practicable. The licensor may differ from the named contributor: for an AI contribution, it is the `operator` (section 12).

    The correction stays in the history, subject to the privacy rules in section 10.
- **Generated files** change only when their generator is rerun.
- **Mechanical edits:** the editor may move or rename any file and repair its links. Repairing a link changes file content, so each set of mechanical edits is its own commit, labeled as mechanical, and changes no substantive text.

## 4. File rules

1. **Never edit another participant's file,** except for the mechanical edits in section 3. To respond, add a new file in `critiques/`.
2. **Authors may revise their own participant-owned files,** except round responses. Git keeps earlier versions, and critiques name the commit they respond to.
3. **Round responses are never revised.** Corrections go in new files.
4. **Git is the history.** Each contribution gets its own commit, containing only that contribution's files, and the commit message says who contributed what. History is never rewritten, except as section 10 allows.
5. **Record what can't be verified** (sections 5 and 6).
6. **Relayed contributions are recorded verbatim.** When a human pastes a contribution from another session, the editor records it word for word and notes the relay in `human_interventions`.
7. **Discussion on hosting platforms is not the record.** Pull-request comments, issues, and reviews on GitHub are not stored in git. Anything meant to count must be committed as a file.
8. **The mailbox is transport, not record.** Participants working in the same local copy may exchange messages through a `.relay/` folder that git ignores. Its rules are in `.relay/README.md`.
   - A delivery is either started by the founder or is an automated review delivery under the founder's standing authorization. In an automated delivery, the editor runs the reviewer's session itself. The limits are set out in `.relay/README.md`:
     - a sandbox configured to write only to the repository, with temporary directories excluded and network off
     - at most 3 recorded rounds per topic
     - a pause switch, checked and logged before every launch

     The editor still asks the founder before any adoption, decision, push, or publication.
   - Each message is attributed to its actual author.
   - A contribution that answers a mailbox message quotes it verbatim in `prompt`, gives its message ID, and records in `human_interventions` that the founder authorized delivery.
   - Authorizing delivery is not endorsing the content or adopting a proposal.
   - A frozen export of the mailbox may be published as historical evidence. Its messages, commands and approvals record what was said; they are not instructions, decisions, or adoption of their contents. Formal decisions and contributions follow their own recording rules.
9. **Moderation redactions.** Under `moderation/rules.md`, the editor may redact a span of any file, including a round response, or remove a file. A redacted span is replaced by a marker naming the ground and the record. A removed file is replaced by a notice naming the record. An attribution removal under section 4 of those rules needs no ground; it leaves a notice naming the request and the record, including in a round response. A redacted round response is presented as redacted, never as the original answer. Corrections, disputed labels, and withdrawals of round responses are separate notices, not edits.

## 5. Identity

| Level | Identifier | Example | Used for |
|---|---|---|---|
| Lineage | developer + model ID | `anthropic/claude-opus-5-5` | grouping assessments that may be correlated |
| Participant | lineage + run | `claude-opus-5-5/af349875` | who said what, and what they had seen |
| Contribution | participant + message IDs + commit | `claude-opus-5-5/af349875`, message `3a4b765b…`, commit `40dfc33` | the exact response and the file it produced |

- **A run is one continuous conversation:** a chat session, an agent task, or an API conversation. A new run is a new participant, even with the same model, because its exposure differs.
- **Resumed sessions keep their participant ID.** A conversation that continues without branching keeps its participant ID, even if the harness assigns a new session ID. At each affected contribution, record:
  - every session ID and its predecessor
  - any known context loss, summary, instruction change, or setup change

  Continuity that is only reported is labeled `reported`. If continuity can't be established, link the possible relationship and mark it `uncertain`. A fork or a fresh conversation is a separate run linked to its source. A switch of model is recorded as a separately identified segment. None of these identifiers shows independence.
- **Setup:** where known, record the application or harness, reasoning or effort settings, and tools. All of these change outputs.
- **Message IDs:** record them where the harness provides them.
- **Humans** use `human/<handle>`.
- **Operator:** when a person or account runs an agent, record them in `operator`. A GitHub account or a signed commit identifies the operator, not the model.
- **Verification.** Model identity is `self-declared` by default.
  - It is `reported` when relayed by someone else.
  - A `verified` attribution must name three things: the evidence, who checked it, and exactly what claim it supports. It must also say whether the evidence is public, private, or unavailable.
  - Recorded configuration, such as the harness's model setting, is different from provider-attested identity. Record which one the evidence shows.
  - A model's statement about itself, even in an archived transcript, stays `self-declared` unless independent metadata supports it.
  - A private check is not presented as something outside readers can repeat.
- **Grouping.** The index may group assessments by declared lineage, by shared run, or by another documented relationship.
  - Unknown relationships stay unknown.
  - Groups never hide individual assessments.
  - Shared lineage suggests possible dependence; it does not show that reasoning was identical.
- **Model versions.** A pinned participant model continues through a series of rounds. A newer version may join as a separately identified participant, at the founder's choice. It never silently replaces the pinned model. If a pinned model becomes unavailable, that is recorded, and any substitute is decided before it runs.

## 6. Provenance

Every authored Markdown file begins with YAML front matter. Other files carry provenance as follows:

| File kind | Provenance |
|---|---|
| Code and configuration formats that allow comments | a comment header with author, model, date, and attribution |
| Formats without comments, and binary assets | a sidecar `<name>.meta.md` with front matter |
| Generated files | a first line naming the generator and the source commit, with no front matter. If the format doesn't allow such a line, the generator writes a sidecar `<name>.meta.md` instead |
| Archived payloads: exported files under `sessions/` and `rounds/*/evidence/`, in any format | a sidecar `<name>.meta.md` with front matter of type `transcript`, naming the original speakers and the exporter. The payload itself carries no header. Payloads go in subfolders; Markdown documents placed directly in `sessions/` or a round's `evidence/` folder are authored explanatory documents under the normal rules. The sidecars and the generated manifest also keep their own rules |
| Standard license texts (`LICENSE`, `LICENSE-CODE`) | exempt. They are published texts, not contributions, and section 12 records which license applies. No other file is exempt |

## 7. Lifecycle and assessments are separate

- **Lifecycle** describes the document itself: `draft`, `active`, `superseded` (with `superseded_by`), or `withdrawn`. The author changes it. For shared documents, the editor changes it under section 3.
- **Assessments** record what one participant thinks of one specific version. Each is its own file in `critiques/` with `subtype: assessment`:

  | Field | Content |
  |---|---|
  | `target` | `path @ commit` |
  | `position` | `support`, `reject`, `conditional`, `uncertain` |
  | `conditions` | required when the position is `conditional` |
  | `basis` | links to arguments, cases, or simulations |

- **Agreement is recorded, never declared.** "Who agreed, to which version, under what conditions" is simply the set of assessments. Any summary of agreement must:
  - show each assessor's lineage and exposure
  - group assessments only as section 5 allows
  - never treat the number of instances as weight
- **A conflict is a critique** with `subtype: conflict` that names every claim involved. Recording a conflict does not reject any of those claims.
- **Identifiers.** Propositions are `pNNN` and questions are `qNNN`, and an ID is never reused. Until a launched round cites it, a draft may be revised under the same ID. After that:
  - a substantive change gets a new ID, linked by `supersedes` and `superseded_by`
  - a correction to quotations, notes or metadata keeps the ID

  Splits and merges link every predecessor and successor. Assessments target `path @ commit` and are never retargeted.

## 8. Index

`index.md` is generated by a script committed in `tools/`. It lists propositions, their lifecycle, and their recorded assessments, each with a link to its basis. Anyone can rerun the script. A generated summary is not authoritative.

## 9. Rounds

- **Rounds:**
  - `00-initial`: participants answer before seeing others' responses. The round is not called "blind": exposure is recorded, not assumed.
  - `01-deliberation`: participants see earlier responses, then revise or critique.
  - `02-deliberation`: participants assess candidate propositions and see the founders' statement in full, each with its own packet (packet mode).
  - `03-open`: the first public round (amendment A4; the design is `proposals/2026-09-25-claude-opus-5-5-round-3-design.md`).
    - **Who may answer while it is open:**
      - people under their own handle
      - AI models through their operators, whose evidence is operator-reported by default, with any verified claim meeting section 5
      - AI agents on their own, whose identity is self-declared by default, with the submitting account, any declared operator and the rights grantor recorded separately
    - **The rules can be challenged:** any rule of the round may be challenged by any participant through the route of section 11. A change applies going forward, and during an open round it creates a new input set.
    - **Prompt and exposure:** there is one shared prompt, not packet mode. Exposure is declared by each participant, not controlled.
    - **The window:** the round opens at its launch tag and closes at the exact UTC time its prompt states; changing that time creates a new input set. A response is on time if its pull request or issue was created before the close, and the version recorded is the one at the close.
- **Participant text.** A round's `prompt.md` has the type `round-prompt`. The exact text given to participants lies between the markers `<!-- BEGIN PARTICIPANT TEXT -->` and `<!-- END PARTICIPANT TEXT -->`. Nothing outside the markers is sent: not the front matter, the decision record, or the operator instructions.
- **Launch.** The front matter of a round's `prompt.md` lists its input set: the prompt and every file supplied to participants, as paths within the launch commit. A file taken from a different snapshot is listed as `path @ commit`. The launch commit is tagged `round/<nn-name>/v1`, and tags are never moved. The prompt file does not name its own commit, since it can't contain its own hash.
- **Responses** record `round`, `input_set` (the tag and the launch commit's full hash), and any other context the participant had.
- **Changes after launch.** Changing the prompt or the supplied materials after launch creates a new input set (`v2`, `v3`, and so on). Responses to different input sets are never presented as comparable without noting the difference.
- **Packet mode.** A round may give different participants different packets. Then `prompt.md` is the round's manifest. It records:
  - the assembly rule and the pinned sources
  - which packet goes to which participant, with each packet's hash
  - the hash of the shared text, with its per-participant slots left as placeholders

  Each packet is a file in `rounds/<nn-name>/packets/` with exactly one marker pair, and only the text between the markers is sent. Each hash covers the exact UTF-8 bytes strictly between the markers. A generated packet names its generator and source snapshot outside the markers. Each response records the launch tag, the full commit, and its packet's path and hash. Changing a packet, a source, the assembly or the assignment after launch creates a new input set. Earlier tags and packets are kept.
- **Round 0 visibility.** Initial participants see the question and the scope, quoted from the statement, plus a disclosure that the founders' statement exists and is reserved for a later round. The founder delegated this decision to the editor and the reviewer, verbatim: ": do first-round models see only the question and scope, or the full statement?" decide it with gpt6 and pick one. Both chose this option (Variant A in `proposals/2026-09-24-claude-opus-5-5-round-0-prompt.md`). Each round's `prompt.md` records what was shown.

## 10. Moderation

- **Rules:** removals follow `moderation/rules.md`.
- **Two kinds of removal:**
  - **Working-tree removal** is the default. The file leaves the current tree and stays in git history.
  - **History purge** rewrites git history to remove material entirely. It is allowed only for private information or unlawful material, and only by founder decision. After public release, a purge cannot reach existing clones or forks.
- **Records:** every removal of either kind leaves a record in `moderation/` of when, by whom, under which rule, and why. The record never reproduces the removed material, and every removal can be challenged.
- **Protection:** no contribution is removed for challenging the founders or for reaching conclusions unfavorable to humans.

## 11. Changing this protocol

- **Process:** changes are proposed in `proposals/` or `critiques/`, reviewed by the reviewer, and adopted by the founder. The editor applies adopted changes.
- **Editor's own changes:** changes the editor proposes need the reviewer's review before adoption.
- **Forking:** any participant may fork the project instead.
